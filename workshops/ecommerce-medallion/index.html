    Module 1 Create the lakehouse & layers

    One schema-enabled lakehouse with bronze / silver / gold schemas.

    Docs: What is a lakehouse Create a lakehouse Medallion architecture

    What it is

    A lakehouse is a database over a data lake. The medallion pattern splits it into three quality layers — bronze (raw), silver (cleansed), gold (curated).

    Why in Fabric

    Every layer is open Delta in OneLake, so Spark, T-SQL and Power BI all read the same copy — no exports between stages.

    What it solves

    Raw data is never overwritten, and each refinement is a clear, auditable step — the foundation for numbers everyone can trust.

    ▸Create lakehouse lh_contosomart~4 min
    WhyThe lakehouse is the home for all three medallion layers as open Delta — one place every engine can read.
    1. In the workspace, select New item → search Lakehouse → Lakehouse.
    2. Name it lh_contosomart and keep Lakehouse schemas enabled.
    3. Select Create. The Lakehouse explorer opens with Tables and Files areas.
    For data prosA lakehouse is a database over a data lake. Tables is your managed schema (Delta); Files is staging for any format — like a landing zone before you model.
    Why one lakehouse?To keep every snippet runnable in a single trial, we use three schemas (bronze, silver, gold) in one lakehouse. In production, Microsoft recommends a lakehouse — or workspace — per layer for governance (see the medallion doc).
    Expected resultlh_contosomart appears in the workspace and opens in the Lakehouse explorer.
    ▸Create the bronze / silver / gold schemas~4 min
    WhySeparate bronze / silver / gold schemas keep raw, cleansed and curated data clearly — and safely — apart.

    Open a new notebook on this lakehouse (Open notebook → New notebook) and run:

    spark.sql("CREATE SCHEMA IF NOT EXISTS bronze")
spark.sql("CREATE SCHEMA IF NOT EXISTS silver")
spark.sql("CREATE SCHEMA IF NOT EXISTS gold")
spark.sql("SHOW SCHEMAS").show()
    Expected resultSHOW SCHEMAS lists bronze, silver, and gold. Keep this notebook — you'll reuse it.

    Module 2 Ingest raw data into Bronze

    Land the three sources exactly as they arrive — no cleansing yet.

    Docs: Ingest data Shortcuts

    What it is

    Ingestion is landing source data into the bronze layer exactly as it arrives — no cleansing, no reshaping.

    Why in Fabric

    You can copy files in, or create a zero-copy shortcut to data that already lives in OneLake, ADLS, S3 or GCS — both land in bronze as Delta.

    What it solves

    Bronze becomes an immutable source of truth you can always replay from, so a bad transform downstream never loses the original data.

    ▸Upload the sample files to Files/raw/~5 min
    WhyBronze must capture the sources untouched so you can always replay from the original if a later transform goes wrong.

    Use the files from this workshop's data/ folder:

    • raw-sales.json — website orders (messy: mixed dates, currencies, test rows)
    • inventory.csv — warehouse stock levels
    • crm-customers.csv — CRM export (with duplicate customers)
    1. In the Lakehouse explorer, right-click Files → New subfolder → name it raw.
    2. Right-click raw → Upload → Upload files and add all three files.
    For data prosBronze keeps the source format untouched — it's your immutable source of truth, like an append-only staging table you never edit by hand.
    Expected resultFiles/raw/ contains the three files.
    ▸Load raw files into Bronze Delta tables~6 min
    WhyTurning the raw files into Delta tables makes them queryable and versioned while still preserving the source shape.

    In the notebook, load each file as-is into the bronze schema:

    sales = spark.read.option("multiline", "true").json("Files/raw/raw-sales.json")
sales.write.mode("overwrite").format("delta").saveAsTable("bronze.sales")

inv = (spark.read.option("header", "true").option("inferSchema", "true")
             .csv("Files/raw/inventory.csv"))
inv.write.mode("overwrite").format("delta").saveAsTable("bronze.inventory")

cust = (spark.read.option("header", "true").option("inferSchema", "true")
              .csv("Files/raw/crm-customers.csv"))
cust.write.mode("overwrite").format("delta").saveAsTable("bronze.customers")

display(spark.table("bronze.sales"))
    Alternative: shortcutsIf the source already lived in OneLake, ADLS Gen2, S3, or Google, you'd create a shortcut in bronze instead of copying — zero-copy, always live.
    Expected resultThree tables appear under Tables/bronze: sales (20 rows), inventory (7), customers (8).

    Module 3 Cleanse into Silver

    Standardize dates, convert currency to USD, drop test rows, and dedupe customers.

    Docs: Use notebooks Delta tables

    What it is

    The silver layer is where raw bronze becomes trustworthy: standardized types, one currency, no test rows, one record per customer.

    Why in Fabric

    A Spark notebook transforms at scale and writes a governed Delta table every engine can read — like a cleansing view, but persisted and open.

    What it solves

    This is exactly where the Monday numbers war ends: mixed dates, four currencies and duplicate customers all get resolved once, for everyone.

    ▸Clean and standardize the sales stream~10 min
    WhyThis is where the Monday numbers war is settled — one date format, one currency (USD), and no test rows.

    The raw orders have three problems the silver layer fixes: inconsistent date formats, four different currencies, and test transactions. Run:

    from pyspark.sql import functions as F

# Illustrative FX rates to USD (teaching values, not live rates)
fx = {"USD": 1.0, "CAD": 0.73, "EUR": 1.09, "GBP": 1.27}
fx_map = F.create_map([F.lit(x) for kv in fx.items() for x in kv])

bronze_sales = spark.table("bronze.sales")

silver_sales = (bronze_sales
    .filter(F.col("is_test") == False)                      # drop test/QA orders
    .withColumn("customer_ref", F.upper(F.trim("customer_ref")))
    .withColumn("order_date", F.coalesce(                   # normalize mixed date formats
        F.to_date("order_date", "yyyy-MM-dd"),
        F.to_date("order_date", "MM/dd/yyyy"),
        F.to_date("order_date", "dd-MM-yyyy"),
        F.to_date("order_date", "yyyy/MM/dd"),
        F.to_date(F.substring("order_date", 1, 10), "yyyy-MM-dd")))
    .withColumn("amount_usd", F.round(F.col("amount") * fx_map[F.col("currency")], 2))
    .select("order_id", "customer_ref", "order_date", "sku", "qty",
            "currency", "amount", "amount_usd", "channel"))

silver_sales.write.mode("overwrite").format("delta").saveAsTable("silver.sales")
display(silver_sales.orderBy("order_date"))
    For data prosThis is your ELT transform layer — like a cleansing view or stored proc, but the output is a governed Delta table every engine can read.
    Expected resultsilver.sales has 18 rows (2 test orders removed), every order_date is a real date, and amount_usd is populated for all rows.
    ▸Match & dedupe customers across systems~8 min
    WhyDuplicate customers inflate counts and split history; one row per customer makes every downstream metric correct.

    The CRM export lists some customers twice with variant country/email values. Standardize the country and keep one row per customer:

    from pyspark.sql import functions as F

crm = spark.table("bronze.customers")

silver_customers = (crm
    .withColumn("web_ref", F.upper(F.trim("web_ref")))
    .withColumn("country", F.when(F.col("country").isin("US", "United States"), "United States")
                            .when(F.col("country").isin("UK", "United Kingdom"), "United Kingdom")
                            .otherwise(F.col("country")))
    .dropDuplicates(["web_ref"])                            # one record per customer
    .select(F.col("web_ref").alias("customer_ref"),
            "full_name", "email", "country", "segment", "signup_date"))

silver_customers.write.mode("overwrite").format("delta").saveAsTable("silver.customers")
display(silver_customers)
    Expected resultsilver.customers collapses to 6 unique customers (the duplicate C-0007 and C-0044 rows merged), each with a standardized country.

    Module 4 Curate Gold business tables

    Shape analytics-ready tables: daily sales, customer lifetime value, inventory status.

    Docs: Medallion architecture Delta tables

    What it is

    The gold layer holds business-ready tables — aggregated, joined and named for the questions people actually ask (daily sales, customer value, reorder status).

    Why in Fabric

    Build gold once in Spark (or a Warehouse) and it's instantly available to Power BI Direct Lake, T-SQL and ML — no per-tool remodeling.

    What it solves

    Analysts stop hand-rolling the same aggregations; everyone reports off the same curated numbers.

    ▸Build the daily sales table~8 min
    WhyA pre-aggregated daily fact means every report and user reads the same revenue numbers — fast.

    Aggregate silver sales into a daily fact table. Do it in PySpark, or preview the equivalent in T-SQL on the SQL analytics endpoint:

    from pyspark.sql import functions as F

daily = (spark.table("silver.sales")
    .groupBy("order_date")
    .agg(F.round(F.sum("amount_usd"), 2).alias("revenue_usd"),
         F.sum("qty").alias("units"),
         F.countDistinct("order_id").alias("orders"))
    .orderBy("order_date"))

daily.write.mode("overwrite").format("delta").saveAsTable("gold.daily_sales")
display(daily)
    -- Run in the lakehouse SQL analytics endpoint (read-only)
SELECT  CAST(order_date AS date)      AS order_date,
        ROUND(SUM(amount_usd), 2)     AS revenue_usd,
        SUM(qty)                      AS units,
        COUNT(DISTINCT order_id)      AS orders
FROM    silver.sales
GROUP BY CAST(order_date AS date)
ORDER BY order_date;
    NoteThe lakehouse SQL analytics endpoint is read-only — great for validating with T-SQL, but to persist gold tables in T-SQL you'd use a Fabric Warehouse as the gold layer (medallion "Pattern 2").
    Expected resultgold.daily_sales has one row per order date with revenue_usd, units, and orders.
    ▸Customer lifetime value (CLV)~6 min
    WhyCurating lifetime value once lets marketing rank customers without re-deriving it in every tool.
    from pyspark.sql import functions as F

clv = (spark.table("silver.sales")
    .groupBy("customer_ref")
    .agg(F.round(F.sum("amount_usd"), 2).alias("lifetime_value_usd"),
         F.countDistinct("order_id").alias("orders"),
         F.max("order_date").alias("last_order")))

# enrich with customer attributes from silver
clv = clv.join(spark.table("silver.customers"), "customer_ref", "left")
clv.write.mode("overwrite").format("delta").saveAsTable("gold.customer_ltv")
display(clv.orderBy(F.desc("lifetime_value_usd")))
    Expected resultgold.customer_ltv ranks customers by USD lifetime value, joined to their name/country/segment.
    ▸Inventory reorder status~5 min
    WhyFlagging reorder in gold turns raw stock levels into the signal that prevents the next stock-out.
    from pyspark.sql import functions as F

status = (spark.table("bronze.inventory")
    .withColumn("needs_reorder", F.col("on_hand_qty") < F.col("reorder_point"))
    .select("sku", "product_name", "category", "on_hand_qty",
            "reorder_point", "needs_reorder"))

status.write.mode("overwrite").format("delta").saveAsTable("gold.inventory_status")
display(status.filter("needs_reorder = true"))
    Expected resultgold.inventory_status flags each SKU; the filtered view shows items at/under their reorder point.

    Module 5 Serve with Direct Lake & Power BI

    Docs: Direct Lake Semantic model & report

    What it is

    A semantic model is the Power BI layer (tables, relationships, measures) that reports sit on. Direct Lake points it straight at gold Delta in OneLake.

    Why in Fabric

    Direct Lake gives Import-mode speed with no scheduled refresh and no second copy — it reads the Delta files in place.

    What it solves

    Priya's report always reflects the latest gold write, with no ETL-into-Power-BI and no stale overnight refresh.

    4. Select Confirm.

    Module 6 Govern & optimize

    Secure sensitive columns/rows and tune Delta for fast, lean reads.

    Docs: OneLake security Row/column security V-Order VACUUM

    What it is

    OneLake security defines table / column / row rules; V-Order, OPTIMIZE and VACUUM keep Delta files fast and lean.

    Why in Fabric

    A security role is enforced once and applies across SQL, Spark and Power BI — you don't re-implement row-level security per tool.

    What it solves

    Lena can hide cost columns and scope rows for viewers, while reads stay fast as the data grows — governance and performance without extra copies.

    ▸Add a OneLake security role (hide cost, filter rows)~8 min
    WhyAnalysts need the data but not the costs — one role scopes columns and rows across every engine at once.

    Give analysts read access to inventory without the unit_cost_usd column and only for their region:

    1. Open lh_contosomart → Manage OneLake security (or Manage roles).
    2. Create a role AnalystRead and grant it on gold.inventory_status and gold.daily_sales.
    3. Apply column-level security to exclude a sensitive column (e.g. cost), and add a row-level filter (e.g. category = 'Beans') to scope the rows.
    4. Add a test Viewer user to the role.
    For data prosOneLake security roles enforce table/column/row rules once and apply them across SQL, Spark, and Power BI — no need to re-implement RLS per tool. Workspace Admins/Members/Contributors already have full data access; roles mainly scope Viewers.
    Expected resultSigned in as the Viewer, querying the table returns only the allowed rows and hides the secured column.
    ▸Optimize Delta with V-Order~4 min
    WhyCompacting and V-Ordering keeps reads fast as data grows, so reports stay snappy over time.
    # V-Order write optimization speeds reads by Power BI / SQL / Spark
spark.conf.set("spark.sql.parquet.vorder.enabled", "true")

# Compact small files and apply V-Order to the gold fact table
spark.sql("OPTIMIZE gold.daily_sales")
    NoteFabric writes Delta with V-Order by default. Target file sizes of 128 MB–1 GB in gold, and use Liquid Clustering (not partitioning) for silver/gold on new implementations.
    Expected resultOPTIMIZE reports the number of files compacted for gold.daily_sales.
    ▸Reclaim storage with VACUUM & wrap up~4 min
    WhyVacuuming reclaims storage from old files while keeping enough history for safe time travel.
    # Remove old data files no longer referenced (7-day minimum retention)
spark.sql("VACUUM gold.daily_sales RETAIN 168 HOURS")
    NoteDelta keeps history for time travel; VACUUM trims files older than the retention window. By default you can't vacuum below 7 days (168 hours), which protects consistency.
