    Module 0 Warehouse vs lakehouse — pick your lane

    Fabric Data Warehouse is an enterprise, T-SQL-first relational warehouse on a lake foundation — full DDL/DML, multi-table ACID, separated compute/storage. Knowing when to reach for it (vs the Spark lakehouse) is the first skill.

    Docs: What is Fabric Warehouse Decision guide

    Learn more Warehouse overview Warehouse vs lakehouse Trial
    ▸ When to choose a Warehouse ~6 min

    What & why: Choose a warehouse for governed, structured, star/snowflake corporate marts developed in T-SQL. Choose a lakehouse for large, unstructured, Spark-driven data. Both store Delta and share the same SQL engine — you can add the other later.

    For data prosThis is your Synapse dedicated SQL pool / classic EDW, reborn as SaaS: no DWU knobs, autonomous workload management, storage/compute separated and scaled independently, data auto-replicated to OneLake as Delta.
    Expected resultYou can justify, for ContosoMart Finance, why the governed star schema belongs in a warehouse.
    ▸ Reuse the ContosoMart workspace ~4 min

    What & why: Same workspace as the rest of the saga so the warehouse can query the lakehouse gold via three-part names later.

    NoteTrial is F4/F64, no Copilot. A warehouse and the lakehouse SQL analytics endpoint can coexist in one workspace.
    Expected resultYou're in ContosoMart-Analytics on Trial capacity.

    Module 1 Create the Warehouse & tables

    A Fabric Warehouse gives you the full T-SQL surface — CREATE TABLE, constraints, transactions. We define a fact and two dimension tables to hold ContosoMart's finance data.

    CREATE TABLE dbo.dim_product (
    product_key    VARCHAR(20)  NOT NULL,

    category       VARCHAR(40)  NULL,

CREATE TABLE dbo.dim_customer (
    customer_key  VARCHAR(20)  NOT NULL,
    customer_name VARCHAR(100) NULL,
    country       VARCHAR(4)   NULL,
    segment       VARCHAR(30)  NULL,
    signup_date   DATE         NULL
);

CREATE TABLE dbo.fact_orders (
    order_id       VARCHAR(20)   NOT NULL,
    order_date_key INT           NOT NULL,
    product_key    VARCHAR(20)   NOT NULL,
    customer_key   VARCHAR(20)   NOT NULL,
    qty            INT           NOT NULL,
    amount_usd     DECIMAL(12,2) NOT NULL
);
    For data prosIdentical shape to any RDBMS. Fabric warehouse constraints (PK/FK) are supported but not enforced — they inform the optimizer and semantic model relationships; enforce quality upstream.

    Module 2 Bulk load with COPY INTO

    COPY INTO is the fast, minimal-setup bulk loader for the warehouse — one T-SQL statement pulls a file straight into a table. We load the three CSVs into the tables you just created.

    Docs: Ingest into the warehouse COPY INTO (T-SQL)

    Learn more COPY INTO Ingestion methods COPY tutorial
    ▸ Upload the CSVs & COPY INTO ~14 min

    What & why: First upload the three files to a lakehouse Files/finance/ folder (or any OneLake path), then load with COPY INTO pointing at those paths. 

    COPY INTO dbo.dim_product
FROM 'https://onelake.dfs.fabric.microsoft.com/<workspace>/<lakehouse>.Lakehouse/Files/finance/dim_product.csv'
WITH (FILE_TYPE = 'CSV', FIRSTROW = 2);

COPY INTO dbo.dim_customer
FROM 'https://onelake.dfs.fabric.microsoft.com/<workspace>/<lakehouse>.Lakehouse/Files/finance/dim_customer.csv'
WITH (FILE_TYPE = 'CSV', FIRSTROW = 2);

COPY INTO dbo.fact_orders
FROM 'https://onelake.dfs.fabric.microsoft.com/<workspace>/<lakehouse>.Lakehouse/Files/finance/fact_orders.csv'
WITH (FILE_TYPE = 'CSV', FIRSTROW = 2);
    For data prosThis is bcp/ BULK INSERT/PolyBase's spiritual successor — parallelized, format-aware, and it reads directly from OneLake or external storage.
    NoteReplace <workspace>/<lakehouse> with your names. FIRSTROW = 2 skips the header row.
    Expected resultSELECT COUNT(*) FROM dbo.fact_orders returns 7; dims return 5 each.

    Module 3 Model the star & encapsulate logic

    A star schema (one fact, many dimensions) is the shape BI tools love. We join fact + dims into a vw_sales view that also computes margin — business logic defined once, reused everywhere.

    Docs: Tables & modeling Warehouse use cases

    Learn more Star schema guidance Warehouse tables Query the warehouse
    ▸ Create vw_sales with margin ~12 min

    What & why: A view hides the joins and centralizes the margin calc so every report agrees on the number.

    CREATE VIEW dbo.vw_sales AS
SELECT
    f.order_id, f.order_date_key,
    p.product_name, p.category, c.country, c.segment,
    f.qty, f.amount_usd,
    (f.amount_usd - f.qty * p.unit_cost_usd) AS margin_usd
FROM dbo.fact_orders  AS f
JOIN dbo.dim_product  AS p ON p.product_key  = f.product_key
JOIN dbo.dim_customer AS c ON c.customer_key = f.customer_key;

SELECT category, SUM(amount_usd) AS revenue, SUM(margin_usd) AS margin
FROM dbo.vw_sales GROUP BY category ORDER BY revenue DESC;
    # Equivalent star join in the lakehouse with Spark SQL
spark.sql("""
  SELECT p.category,
         SUM(f.amount_usd) AS revenue,
         SUM(f.amount_usd - f.qty*p.unit_cost_usd) AS margin
  FROM fact_orders f
  JOIN dim_product p ON p.product_key = f.product_key
  GROUP BY p.category ORDER BY revenue DESC
""").show()
    For data prosSame star, two engines: the warehouse view is classic T-SQL; the Spark version reads the same Delta data. Pick the tool your team knows — the data doesn't move.
    Expected resultThe grouped query returns revenue + margin per category (Coffee highest).

    Module 4 Cross-database query (zero copy)

    Data lives in the warehouse and the lakehouse. Fabric lets a single T-SQL query join across them by three-part name — no export, no duplication. Here the finance warehouse joins the medallion gold in the lakehouse SQL endpoint.

    Docs: Cross-database queries

    Learn more Query & cross-DB Lakehouse SQL endpoint
    ▸ Join warehouse to lakehouse gold ~12 min

    What & why: In the same workspace, add the lakehouse to the warehouse's query view and reference its tables by three-part name [item].[schema].[table]. Enrich finance facts with the medallion gold customer LTV. 

    -- From wh_contoso_finance, join to the lakehouse SQL analytics endpoint
SELECT s.customer_key, s.country,
       SUM(s.amount_usd) AS finance_revenue,
       MAX(g.lifetime_value_usd) AS crm_ltv
FROM dbo.vw_sales AS s
JOIN [lh_contosomart].[gold].[customer_ltv] AS g
  ON g.customer_id = s.customer_key
GROUP BY s.customer_key, s.country
ORDER BY finance_revenue DESC;
    For data prosThree-part naming across a warehouse and a lakehouse endpoint — like cross-database queries in SQL Server, but the "databases" are different Fabric items sharing one OneLake.
    NoteBoth items must be in the same workspace (or added to the query). The lakehouse gold table comes from the medallion lab; adjust names if yours differ.
    Expected resultOne row per customer with finance revenue next to CRM lifetime value.

    Module 6 Govern & optimize

    A finance warehouse holds sensitive numbers. Lock it down with T-SQL security and lean on the engine's autonomous performance — no DWU knobs to tune.

    Docs: Warehouse security & performance

    Learn more Warehouse security Row-level security Performance guidelines
    ▸ Grant least-privilege + row-level security ~12 min

    What & why: Give an analyst read access to the view but not the raw cost table, and restrict rows by country with RLS.

    -- Column/object security: expose the view, not raw costs
GRANT SELECT ON OBJECT::dbo.vw_sales TO [analyst@contoso.com];
DENY  SELECT ON OBJECT::dbo.dim_product (unit_cost_usd) TO [analyst@contoso.com];

-- Row-level security: analyst sees only Canada
CREATE FUNCTION dbo.fn_country_filter(@country VARCHAR(4))
RETURNS TABLE WITH SCHEMABINDING AS
RETURN SELECT 1 AS ok WHERE @country = 'CA' OR USER_NAME() = 'dbo';

CREATE SECURITY POLICY dbo.sales_rls
ADD FILTER PREDICATE dbo.fn_country_filter(country) ON dbo.vw_sales
WITH (STATE = ON);
    For data prosSame RLS predicate function + security policy you know from SQL Server — enforced by the shared Fabric SQL engine across the warehouse and the SQL analytics endpoint.
    NotePerformance is autonomous: no distributions/indexes to design. Keep statistics fresh and prefer the star for optimizer-friendly plans.
