    Module 0 What a Fabric data agent is (and isn't)

    A Fabric data agent lets people ask questions in plain English and get structured, human-readable answers over the data your org already stored in OneLake — no SQL, DAX or KQL required.

    Docs: Data agent concept Use it with Foundry

    ▸How it works under the hood~5 min

    Intent: understand the pipeline before you build, so you can reason about accuracy and governance later.

    The data agent uses an LLM (via the Azure OpenAI Assistant APIs) to: parse the question, pick the most relevant source, generate a read-only query, validate it, run it, and format a human-readable answer. It translates language to the right dialect per source:

    • NL2SQL for lakehouse & warehouse (relational).
    • NL2DAX for Power BI semantic models.
    • NL2KQL for KQL databases / Eventhouse (time-series).
    • Microsoft Graph queries for org data via Graph.
    For data prosThink of it as a governed natural-language front end that writes the SELECT for you — it never issues INSERT/UPDATE/DELETE.
    Expected resultYou can explain the six steps: parse → identify source → generate → validate → execute → respond.
    ▸Data agent vs Copilot~4 min

    Intent: know when to reach for a data agent instead of Copilot.

    • Copilot is preconfigured and helps you author inside Fabric (notebook code, warehouse queries).
    • Data agent is a standalone, highly configurable artifact you tune with instructions and examples, and that external systems — Copilot Studio, Azure AI Foundry, Teams — can call to build end-to-end agentic workflows.
    Why this mattersThat last point is the whole reason for Part 2: the data agent is the bridge that lets a Foundry agent reason over your Fabric data.

    Module 1 Prerequisites & tenant settings

    The data agent needs a paid capacity, at least one data source with data, and a couple of tenant settings switched on. This is where the free trial stops.

    Docs: Prerequisites Tenant settings

    ▸Confirm capacity & sources~6 min

    Intent: make sure your ContosoMart estate qualifies before you build.

    • A paid F2 or higher capacity, or Power BI Premium P1+ with Fabric enabled.
    • At least one source with data: a warehouse, lakehouse, Power BI semantic model, KQL database, mirrored database, or ontology — you need read access.
    Not on the trialThe free 60-day Fabric trial can't run a data agent — you need a paid capacity assigned to ContosoMart-Analytics.
    Expected resultYour workspace is on an F2+/P1+ capacity and shows the gold lakehouse, warehouse and eventhouse from Part 1.
    ▸Enable the AI tenant settings~5 min

    Intent: allow the AI features the data agent relies on.

    An admin enables, per the tenant-settings doc, cross-geo processing and cross-geo storing for AI where your deployment requires it. Confirm your users have read access to each source.

    For data prosCross-geo settings matter because the data agent can't execute a query when a source's capacity is in a different region than the agent's.
    GovernanceIf Purview DLP or access-restriction policies apply to a source, they will constrain what the agent can query and return.

    Module 2 Create the agent & add sources

    Create a data agent in ContosoMart-Analytics, then add up to five sources and choose the specific tables it should use.

    Docs: Create a data agent Selecting sources

    ▸Create "ContosoMart Analyst"~5 min

    Intent: stand up the artifact you'll configure and publish.

    In ContosoMart-Analytics select New item → Data agent, name it ContosoMart Analyst. Building it is like building a report: design and refine, then publish and share.

    Expected resultAn empty ContosoMart Analyst data agent opens, ready for sources.
    ▸Add up to 5 sources & pick tables~12 min

    Intent: point the agent at the trusted ContosoMart data, one source at a time.

    Add these (any combination up to five), and for each choose only the relevant tables:

    • Lakehouse lh_contosomart — gold tables: daily_sales, customer_ltv, inventory_reorder, demand_forecast.
    • Warehouse wh_contosomart — the star: fact_orders, dim_customer, dim_product.
    • Power BI semantic model — the ContosoMart sales model for governed measures.
    • KQL database (Eventhouse) — clickstream, warehouse_sensors.
    Tables, not filesFor a lakehouse, select tables — the agent doesn't read standalone CSV/JSON files. Ingest files to tables first (you did this in Part 1).
    KQL tipPick only the KQL tables most relevant to typical questions, and encourage time filters on high-volume event/time-series data to keep answers fast.
    Expected resultThe agent lists your four sources with the chosen tables under each.

    Module 3 Add context: instructions & example queries

    Instructions and sample question/query pairs are what make the agent accurate — they tell it which source answers which kind of question, in ContosoMart's own language.

    Docs: Adding context Intent layers

    ▸Write routing instructions~8 min

    Intent: steer the agent to the best source and define ContosoMart terms.

    Add instructions like these (developer intent):

    You are the ContosoMart analytics assistant. Answer only from the connected sources.
- Financial metrics (revenue, margin, LTV): use the Power BI semantic model.
- Raw / detailed sales and inventory: use the lakehouse gold tables.
- Order-level star-schema questions: use the warehouse (fact_orders + dims).
- Clickstream, cart and cold-store sensor questions: use the KQL database, and apply a time filter.
Definitions: "revenue" = net sales in USD; "reorder point" = inventory_reorder.threshold;
a "week" starts Monday. Currencies are already normalized to USD in gold.
    For data prosThis is the same discipline as a good semantic layer — name your metrics once so every answer is consistent.
    ▸Add example question/query pairs~8 min

    Intent: show the agent how a good answer looks for common questions.

    Add sample pairs (up to 100 per source). Example for the warehouse:

    Q: What were total sales last week?
SQL: SELECT SUM(net_amount_usd) AS sales
     FROM fact_orders
     WHERE order_date >= DATEADD(week, -1, CAST(GETDATE() AS date));
    NoteSample question/query pairs aren't currently supported for Power BI semantic model sources — use instructions there instead.
    Expected resultEach relational source has a few representative examples the agent can generalize from.
    ▸Understand intent precedence~4 min

    Intent: know why your instructions can be overridden — by design.

    Four layers, highest to lowest: Organizational (tenant policy) → Role-based (workspace governance) → Developer (your instructions/examples) → User (the question). Higher layers always win.

    GuardrailIf an instruction or prompt tries to bypass read-only behavior or reach out-of-scope sources, the agent refuses or redirects per the precedence model.

    Module 4 Test it — the ContosoMart questions

    Ask the questions the Monday standup used to argue about, and watch the agent route, generate and answer — read-only, governed, and cited to a source.

    Docs: How it answers & limits

    ▸Ask across all four sources~10 min

    Intent: confirm each source answers the right kind of question.

    • "What were total sales last week?" → warehouse / gold.
    • "Who are our top 10 customers by lifetime value?" → semantic model / customer_ltv.
    • "Which SKUs are below their reorder point right now?" → inventory_reorder.
    • "How many carts were abandoned yesterday?" → KQL clickstream with a time filter.
    Expected resultEach answer comes back as a small table or summary, and the agent shows which source it used.
    ▸Know the limits~4 min

    Intent: set expectations before real users ask.

    • Responses are capped (currently 25 rows × 25 columns) — it's for conversational insight, not full extracts.
    • Read-only: no create/update/delete, and it won't trigger notebooks or anomaly jobs.
    • No unstructured files (.pdf/.docx/.txt) — that's what Foundry IQ is for in Act 11.
    • English only today; you can't change the underlying LLM.
    TipIf a follow-up looks truncated, start a new chat — prior turns can constrain later answers (e.g. a 25-row cap carries forward).

    Module 5 Govern, publish & share

    Publishing turns your draft into a shareable, governed endpoint — and gives you the identifiers Act 10 needs to connect it to Azure AI Foundry.

    Docs: Share & permissions Purview + Fabric

    ▸Confirm governance carries through~5 min

    Intent: make sure the agent honors the same rules as direct access.

    Purview policies apply to the sources the agent queries: DLP and access-restriction policies can truncate or block answers, sensitivity labels are respected, and RLS/CLS on semantic models still applies. Prompts and responses can be subject to Purview audit and eDiscovery.

    For data prosLeast privilege by design: the agent uses the requesting user's permissions, so it can never surface data that user couldn't already see.
    ▸Publish & share with least privilege~8 min

    Intent: make the agent usable — and consumable by Foundry later.

    • Publish the agent so it's active.
    • Share it, giving each user at least READ on the agent and the minimum permission on each underlying source (Read on lakehouse; SELECT on warehouse tables; Reader on the KQL DB; Read on the semantic model).
    • Optionally connect the workspace to Git and use deployment pipelines to promote dev → prod.
    # The published agent's URL contains the two GUIDs Foundry will need in Act 10:
# .../groups/<workspace_id>/aiskills/<artifact_id>...
# Note them now — you'll paste them into the Foundry "Microsoft Fabric" connection.
    Expected resultA published ContosoMart Analyst agent, shared to your test users, with the workspace_id and artifact_id noted.
    Heads-up for Act 10The Fabric tool uses identity passthrough — service-principal auth isn't supported, and each end user needs access to the agent and its sources.
