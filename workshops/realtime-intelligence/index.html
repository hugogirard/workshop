    Module 0 Set up & understand real-time

Real-Time Intelligence answers "what is happening right now?" — a cart being abandoned this minute, a cold-store fridge warming up before the stock spoils.     Module 1 Create the Eventhouse & KQL database

    An Eventhouse is the storage + analytics engine for events. It auto-organizes data by arrival time so you can run fast time-series queries over huge volumes — it's the "lake in motion" that everything else in this lab feeds and reads.

    Docs: Eventhouse overview Create a KQL database

    ▸ Create Eventhouse eh_contoso_rti ~5 min

    What & why: Creating the Eventhouse gives you a KQL database of the same name automatically — that database holds the tables your streams land in.

    In the workspace: + New item → Eventhouse, name it eh_contoso_rti. Open it and note the child KQL database.

    For data prosThe Eventhouse is the server; the KQL database is the database; KQL tables are your tables. Familiar shape — new engine tuned for append-only, time-partitioned data.
    Expected resultAn Eventhouse eh_contoso_rti with an empty KQL database appears in the workspace.
    ▸ Create the target KQL table ~8 min

    What & why: The stream needs a typed landing table. Run this in the KQL database Explore your data query editor to create the raw clickstream table (our "bronze in motion").

    .create table Clickstream (
    event_id: string, ts: datetime, session: string,
    customer_ref: string, page: string, event_type: string,
    device: string, geo: string, value_cad: real
)

    Also create the sensor table for Module 3/5:

    NoteKQL control commands start with a dot (.create). Keep column names matching the sample files exactly so ingestion maps cleanly.

    Module 3 Shape & query with KQL (silver in motion)

    KQL turns raw events into insight. Here you normalize the messy customer_ref, compute the checkout funnel, measure a 5-minute cart-abandon rate, and detect the cold-store temperature excursion — the streaming equivalent of the medallion "silver" cleanse.

    Docs: KQL overview Eventhouse

    Learn more KQL reference summarize bin() windows
    ▸ Normalize & explore the funnel ~10 min

    What & why: The web app emits mixed-case customer refs (C-0007 / c-0007). Standardize them so events join the CRM cleanly, then count each funnel stage.

    Clickstream
| extend customer_ref = toupper(customer_ref)
| summarize events = count() by event_type
| order by events desc
    -- KQL DBs also accept T-SQL for simple queries:
SELECT event_type, COUNT(*) AS events
FROM Clickstream
GROUP BY event_type
ORDER BY events DESC;
    For data prossummarize ... by is GROUP BY; extend is a computed column; the pipe | chains operators left-to-right instead of nesting.
    Expected resultCounts for page_view, add_to_cart, purchase, cart_abandon.
    ▸ Windowed cart-abandon rate ~10 min

    What & why: A single abandon is noise; a spike is a signal. Bin events into 5-minute windows and compute the abandon rate — this is the metric Activator will watch in Module 5.

    Clickstream
| where event_type in ("add_to_cart", "cart_abandon", "purchase")
| summarize
    added   = countif(event_type == "add_to_cart"),
    abandon = countif(event_type == "cart_abandon")
    by bin(ts, 5m)
| extend abandon_rate = todouble(abandon) / iff(added == 0, 1, added)
| order by ts asc
    For data prosbin(ts, 5m) is a time-bucket (like DATE_TRUNC to a 5-min grid); countif is a conditional aggregate.
    Expected resultOne row per 5-min window with an abandon_rate column between 0 and 1.
    ▸ Detect the cold-store excursion ~8 min

    What & why: Cold-store stock spoils above ~6 °C. Find sensor readings that breach the threshold so we can alert before inventory is lost.

    Sensors
| where zone == "cold-store" and temp_c > 6.0
| project ts, sensor_id, warehouse, temp_c, door_open
| order by ts asc
    NoteSENS-01 in YYZ-1 breaches after a door_open — a realistic root-cause you can show on the dashboard.
    Expected resultTwo rows for SENS-01 at 6.8 °C and 8.5 °C.

    Module 4 Build a Real-Time dashboard (gold in motion)

    A Real-Time dashboard pins KQL queries as auto-refreshing tiles — seconds from ingest to insight, for anyone, no notebook required. This is the "serve & visualize" layer for streaming data.

    Docs: Create a Real-Time dashboard

    Learn more Real-Time dashboards Dashboard parameters
    ▸ Pin tiles for purchases, abandon rate & temperature ~15 min

    What & why: Three tiles tell the ops story at a glance: revenue flowing in, carts being lost, and a fridge warming up. Create a Real-Time Dashboard, add a data source (the KQL database), then add tiles from these queries.

    Tile 1 — purchases per minute (stat / line):

    Clickstream
| where event_type == "purchase"
| summarize revenue_cad = sum(value_cad), orders = count() by bin(ts, 1m)
| order by ts asc

    Tile 2 — 5-min abandon rate (line): reuse the Module 3 abandon-rate query.

    Tile 3 — cold-store temperature (line, one series per sensor):

    Sensors
| where zone == "cold-store"
| project ts, sensor_id, temp_c
| render timechart
    NoteSet the dashboard auto-refresh (e.g. every 30 s) and a time range so tiles update as new events land.
    Expected resultA saved dashboard with three live tiles; the temperature tile visibly spikes for SENS-01.

    Module 5 Act on events with Activator

    Activator turns insight into action: it watches a stream, KQL query, or dashboard tile and, when a condition holds, sends an alert or kicks off a Fabric job / Power Automate flow. This is what makes real-time actionable, not just observable.

    Docs: What is Activator

    Learn more Activator intro Create rules Alert from a tile
    ▸ Alert on a cold-store temperature breach ~12 min

    What & why: A warming fridge is money spoiling. Create an Activator rule so operations gets pinged the moment temperature crosses the line — before the stock is lost.

    From the cold-store temperature tile: … → Set alert. Condition: temp_c is greater than 6, grouped by sensor_id, sustained for 10 min. Action: email / Teams to the ops channel.

    For data prosThis is a database trigger for the physical world — declarative condition → action, but over a live event feed instead of table DML.
    NoteTrial email/Teams actions work; Power Automate actions may need extra licensing. Grouping by sensor_id avoids one noisy sensor masking another.
    Expected resultThe rule shows Active; a test alert fires for SENS-01.
    ▸ Alert on a cart-abandonment spike ~10 min

    What & why: A sudden jump in the abandon rate can mean a broken checkout or a pricing glitch — worth an instant heads-up to the growth team.

    Create an Activator from the abandon-rate query: condition abandon_rate > 0.5 over a 5-min window; action: notify the growth channel.

    Expected resultA second Active rule; triggering history shows it evaluated your windows.

    Module 6 Connect to OneLake & govern

    Turning on OneLake availability mirrors your KQL tables to OneLake as one logical Delta copy — so the same events are readable by Spark, T-SQL and Power BI Direct Lake, and can join the medallion gold tables. One copy, every engine.

    Docs: OneLake availability (one logical copy) Direct Lake

    Learn more One logical copy Direct Lake RTI overview
    ▸ Enable OneLake availability & join to gold ~10 min

    What & why: Real-time and batch shouldn't be silos. Exposing the events in OneLake lets you enrich them with the medallion CRM/gold — e.g. attach customer lifetime value to a live abandoning cart.

    In the KQL database table policy → OneLake availability, turn it On for Clickstream. Then, from the lakehouse SQL analytics endpoint, join to the gold customer table from the medallion lab: 

    -- Enrich a live abandoning cart with batch CLV (conceptual join)
SELECT c.customer_ref, c.value_cad, g.lifetime_value_usd
FROM Clickstream AS c
JOIN gold.customer_ltv AS g
  ON UPPER(c.customer_ref) = g.customer_id
WHERE c.event_type = 'cart_abandon';
    For data prosThis is the "one copy, multi-engine" promise: KQL wrote it, T-SQL reads it, Power BI Direct Lake serves it — no export, no duplicate pipeline.
    NoteOneLake availability adds a Delta copy in OneLake; the KQL engine still owns the hot path. Governance (workspace roles, sensitivity labels) applies just like the medallion lab.
